# 从「看起来能用」到可维护：Inkroam 工程复盘

日期：2026-09-26。检查基线：`ddedf86`。本文只做复盘，不意味着已经实施下面的整改，也不授权重构现有视觉。

## 结论：有类似问题，但不是没有工程基础

这张图对我们有警示意义。Inkroam 已经有组件、工具函数、测试、构建、部署和设计文档，不是纯粹复制粘贴的演示页；但部分迭代确实出现了「先补到看起来正确，再补另一个副作用」的路径。

问题不在于使用AI，也不在于实现快，而在于验证深度没有跟上改动影响范围。漂亮的界面、更多文档、更多测试文件，都不能自动证明底层结构可靠。相反，复杂架构也不是目标：一个静态博客不需要照图增加数据库、服务层或微服务。

## 本次证据范围

- 当前源码：`main.css`、`AppearancePanel.vue`、`useSearchPopover.ts`、`page-scroll.ts`、`PageScrollbar.vue`。
- 当前测试：`check-all.mjs` 及外观、目录、滚动、搜索与产物检查脚本。
- 当前文档：视觉系统、界面组分、弹窗规范，以及本地忽略的工作断点。
- 当前部署：`.github/workflows/deploy.yml`；本次提交对应的 [Actions 36226600011](https://github.com/AdhocHorizon813/inkroam/actions/runs/36226600011) 已完成且 success。
- 本次不是全仓安全审计、性能测量或跨浏览器验收。历史截图与用户反馈能证明具体观感问题，不能证明所有环境都正确。

## 1. CSS 出现了补丁叠补丁

**证据**：本次读取的 `main.css` 约3740行，同类背景、材质和明暗规则分散在多处。背景早期36%光斑被后续规则覆盖，浅色纯色7%/4%又被9%/6%覆盖；这些覆盖已经需要专门写进视觉文档解释。日期输入的内层焦点框原本试图局部去除，仍被现代主题更高优先级规则覆盖，最后追加限定的 `!important` 才消除双框。

**影响**：一条规则存在，不等于它最终生效。维护者需要理解文件顺序、选择器优先级、变量继承和主题分支，才能判断实际样式。继续追加修补会让下一次修复更难。

**责任反思**：此前我在没有计算样式证据时，过快地把「写了规则」描述成「问题修好了」。本地契约检查能保护规则文本，不能证明浏览器最终选择了它。

**改进**：先为一个有限区域整理最终有效规则，再合并该区域的重复声明；每次整理前后对照相同视口、主题、状态截图。不要一次重写整个CSS文件，也不要为了去掉 `!important` 而破坏键盘焦点。

## 2. 局部美化曾经触碰全局滚动契约

**经过**：为了处理筛选前后横移和滚动条白边，先后尝试根滚动条预留、根overflow和轨道样式；期间用户反馈导航不再常驻。后来桌面改用 `.page-scroll`，并补上目录、锚点、回退恢复及滚动条逻辑。

**当前事实**：仓库已通过 `page-scroll.ts` 集中提供滚动访问接口，`PageScrollbar.vue` 的装饰拇指不接管指针输入。这比零散替换 `window.scrollY` 更有结构，但仍引入了桌面容器滚动与手机原生滚动两条路径。

**影响**：滚动条不是纯装饰，它与sticky定位、历史位置、锚点、弹层跟随、错误页和输入设备相关。只验证白边消失，不足以验收整项改动。

**改进**：每次修改滚动所有权必须列出这些消费者，至少检查长短页切换、导航常驻、目录跳转、刷新/后退、弹层打开后滚动、手机触摸及错误页。原则是维护统一滚动接口，不再让新组件各自猜测滚动容器。

## 3. 测试数量与真实体验覆盖不是一回事

**证据**：`check-all.mjs` 当前包含15组常规检查，加 `--built` 为18组。多个脚本使用VM模拟Vue状态或断言源码片段，并明确输出不包含浏览器视觉检查。它们对日期边界、偏好迁移、搜索分组、链接和布局契约很有用。

**缺口**：模拟回调不完整复现真实Vue调度、CSS级联、焦点迁移、原生popover/dialog和合成层取样。某个CSS数值出现在源文件中，不等于它生效；测试通过也不能证明材质好看、没有叠框、动画方向正确。

**改进**：保留便宜的逻辑测试，但补少量高价值真实浏览器用例，而不是单纯增加正则断言。优先选导航常驻、日期焦点、弹层翻转收起、默认设置确认四条路径。浏览器不可用时，明确标为「逻辑通过，视觉待验收」，不能用绿色套件数量替代这一缺口。

## 4. 参数调整有时早于根因验证

**例子**：浅色弹窗被反馈没有模糊时，源码确有28px backdrop-filter。降低白底不透明度可以改善感知，但没有实机计算样式与像素对照时，不能断言唯一原因就是白底太厚。类似地，混色12%/6%是设计选择，不是客观最优值。

**改进**：先区分「状态没传到CSS」「规则被覆盖」「滤镜取样边界不对」「滤镜有效但被底色遮住」四类情况。固定坐标、背景、视口、滚动位置和等待时间，只改变一个变量。用户肉眼确认应记录为观感反馈，不包装成量化测量。

## 5. 设置复杂度正在集中到一个组件

**证据**：`AppearancePanel.vue` 约760行，集中了界面、持久化、v4/v5兼容、默认设置、新老访客判断、背景上传、系统明暗响应、材质应用和确认弹窗。已有 `LIGHT_DEFAULTS`、`DARK_DEFAULTS`、`LEGACY_DEFAULTS`，但SSR首帧属性和CSS兜底仍要人工保持一致。

**风险**：增加一个小开关，可能同时涉及初值、存储恢复、坏值处理、reset、CSS属性、受管范围和文档。漏一个地方就会出现「刷新恢复错误」或「切主题改掉手动选择」。历史断点已记录过默认值迁移造成观感改变的事故。

**已有改进**：默认值与旧偏好兜底被显式区分；新老用户、取消/确认、恢复默认等已有行为测试。应保留这些约束，而不是为了减少代码行数把它们混回一起。

**下一步**：先把偏好规范化与迁移提取成可独立测试的纯函数，再考虑拆视觉组件。特别核对真实Vue深层watch中的新旧值比较：源码有依赖 `from` 判断离散变化的逻辑，当前VM测试不足以确认真实响应式对象场景是否按预期触发转场。这是待验证风险，不在本文中宣布已复现。

## 6. 文档记录充分，但当前规范与历史记录混杂

**证据**：`ui-components.md` 同时保留「不创建独立滚动容器」、后续「桌面搬进.page-scroll」以及更早的根滚动条预留说明，靠「本条替代下文」解释。工作断点适合追加历史，设计规范长期如此会误导接手者。

**影响**：文档越多，不代表越可信。读者可能只读到过期段落；源码已改而表格没改，也会让下一轮工作依据错误事实。

**改进**：正式规范只保留当前实现，历史过程移到复盘或决策记录；状态固定为「已实现 / 建议 / 已废弃 / 未验证」。断点可以详细追加，但不得替代可提交的当前规范。此次透明度建议与实际参数分开记录，就是应继续沿用的做法。

## 7. 发布验证没有完全自动化

**事实**：本次本地typecheck、生产generate、18/18产物回归通过，且对应GitHub工作流已success。但当前部署YAML执行的是 `npm ci`、`npm run generate`、上传与Pages部署，没有显式执行typecheck或 `npm run check -- --built`。

**风险**：依赖操作者每次记得跑检查；下一次直接push仍可能部署通过构建但违反回归约束的版本。构建成功、推送成功、工作流部署成功、线上页面实际正常是不同证据层级。

**改进**：把类型检查与源码/产物回归加入CI门禁，再增加小范围线上smoke检查。先保证失败会阻止发布，不必急着搭建复杂监控平台。

## 我们已经做对的部分

- 产品审美有明确文档与用户约束，不是每次另造一套组件风格。
- 搜索分组、日期计算、滚动访问、弹层定位已有共享模块，部分逻辑可独立测试。
- 静态产物检查覆盖18组套件及本次50个HTML、1347个本地链接目标，而不仅是编译。
- 偏好迁移、取消不改设置、草稿不公开等行为有明确回归约束。
- 原生dialog/popover承担顶层与部分焦点行为，避免不必要的手写替代。
- 提交、工作断点、设计规范和部署状态有记录，临时文件不入库。

这些是工程基础，不该因为一张漫画就全盘否定；但也不该拿它们作为「已经足够可靠」的证明。

1. 写明预期行为与禁止改变的部分，列出跨组件影响。
2. 先观察失败证据，再决定修参数、修样式优先级还是修结构。
3. 一次只改一个原因；若第二次补丁仍不成立，停下来重新定位，不继续堆覆盖。
4. 分别报告逻辑、构建、浏览器、线上四层证据，缺哪层就写哪层。
5. 同步当前规范，历史留给复盘；未实施建议不能混进完成清单。

最终目标不是「写得像工程师」，而是让下一次小改动仍然可预测、可验证、可回退，同时不损伤用户已经认真设计的界面。
