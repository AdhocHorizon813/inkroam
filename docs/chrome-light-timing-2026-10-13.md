日期：2026-10-13。基线 HEAD：fb4ec33。本轮仅开发态探针，不修改正式设计，不提交部署。

## 后续产品决定与阶段收尾

上述描述是采样时的状态。用户随后要求将同步/延迟作为阅读外观的独立偏好，并明确默认同步；现已实现，层次感关闭时禁用。桌面延迟选项保留440ms，移动端无宽度动画，保持同步。另修复禁用默认设置后壁纸仍跟随明暗切换的问题，相关回归与类型检查通过。

用户已授权本批提交部署，导航栏性能调查暂告一段落。这是保留选择后的产品决定，不是证明Chrome性能瓶颈已彻底消失；以上测量及限制仍有效。

## 条件与方法

Chrome 155，1707×876 CSS px，DPR 1.5，modern/dark/liquid，自定义背景，depth=defined；导航 backdrop 为 blur(14px) saturate(1.35)，内容为 blur(5px) saturate(1.25)。同一页面内按 440 / 0 / 0 / 440 ms（ABBA）切换光效延迟，其余曲线、时长、终值保持原状。

每组先回顶等待1700ms，然后分别采样静止、滚至100、回到0，各1600ms。每帧验证 visible/hasFocus，超过等于500ms间隔或5秒超时判无效。本轮四组均完成，无错误。三处计算样式（.nav-depth-light、.depth-receivers__cast、.site-header::after）分别确认0.44s或0s。

指标是 requestAnimationFrame 回调间隔，不等于实际呈现帧率、GPU执行时间或输入延迟。没有本轮trace，不能从此推断具体GPU瓶颈。每种条件仅两次重复，极值不能视为稳定分布。

## 结论与限制

- 并行没有显著抬高前440ms的典型间隔：滚至100中位31.7–32.5，对照31.1–34；回顶30.2–31.1，对照29.8–30.2。范围接近，不能称为确定的典型性能损失。
- 并行起始极值更高：滚至100为102.9–105.2，对照73.5–95.6；回顶57.4–79，对照37.8–49.4。样本小，但两个方向均呈相同趋势。
- 并行更早恢复：440–1000ms中位6.1–6.2，对照24.3–26.6。此处是固定时间窗口，不是两条件都处在同一动画阶段；这正反映并行缩短了高负荷持续区间。
- 四次动作首秒>16.7ms计数合计：延迟128，并行63；>50ms计数：延迟3，并行6。不能只挑其中一种指标声称全面胜出。
- 结论是“较短的负荷区间，但较高的起始尖峰”，不是“同步一定更差”或“已经修复”。当前不直接替换正式延迟设计。若继续，应针对起始尖峰录trace或试短延迟，避免再次盲目大改材质。
