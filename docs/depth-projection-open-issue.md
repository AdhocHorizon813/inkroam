# 导航投影的纯 CSS 替换：完整报告

> **2026-10-06 实施更新**：下文保留历史论证；本轮没有采用 A/B，而是在原近/远模型内修复。`DepthReceivers.vue` 已保持启用期 SVG 挂载、只凭导航有效性接管旧光条，并将 SVG/遮罩限制到导航底部加远层位移与 6σ 的顶部区域。普通滚动使用缓存卡片坐标，导航实时测量；ResizeObserver、模式/窗口变化、路由及 page:finish 刷新缓存。卡片静态阴影与导航冻结配方未变。详见 `docs/depth-receivers.md` 最新章节。类型检查与32项检查通过；尚未浏览器/GPU验收，因此“不再判空闪回”有逻辑测试证据，但“全部滚动卡顿已解决”没有证据。
>
> **论证边界纠正**：本文“纯 CSS 只能二选一/无解”仅适用于文中比较的两个方案，不是所有 CSS 能力的不可实现证明；SVG 外框面积也不等于浏览器实际滤镜分配面积。Gaussian 在3σ外不严格为零。本次保留6σ余量，仍不宣称数学上的完全相同或像素验收已通过。

2026-10-06 归档。**结论：方案 A 与方案 B 都暂缓实施，保持现状**（接光层继续承担导航投影，卡片影继续用 `depth.css` 里的静态 `box-shadow`）。本文是**自包含**的完整报告：包含参照模型、两种替换方案、全部视觉/非视觉损失、暂缓理由、将来的判定顺序、现状快照与验收判据。不依赖其他文档即可读懂。

## 0. 一句话摘要

```text
参照模型（现在的 SVG 接光层）＝ 一个锚点（视口）+ 两种衰减（卡片上强、背景上弱）
纯 CSS 只能二选一：
  保住"两种衰减" → 必须把光画在卡片上 → 锚点从视口变成卡片（V8/V9，无解）
  保住"锚点"     → 只能是一条视口光带   → 放弃两种衰减（= 方案 A）
两头都不划算 → 暂缓；先把性能量出来再决定。
```

## 1. 背景

### 1.1 这是什么项目、视觉系统长什么样（给没看过仓库的人）

```text
站点：Nuxt 静态站（Vue SFC + 手写 CSS，无 CSS 框架、无 WebGL）。
视觉系统有两套「外观」+ 两套「明暗」：
  data-visual = modern（现代幻境，唯一有景深的一档） / classic（纸媒，扁平）
  data-depth  = soft（轻柔） / defined（鲜明）  —— 只对 modern 生效
  data-color-mode = dark / light
  data-display-mode = 正常 / 专注（专注会隐藏导航）
层叠顺序（自下而上，实测值）：
  .ambient-backdrop 固定背景层 z-index -2  →  辉光斑 z-index -1  →  正文内容
  →  SVG 接光层 z-index 2（position: fixed; inset: 0; pointer-events: none）
  →  .site-header 导航 sticky z-index 30  →  外观面板 z-index 80
```

「景深」由三部分构成：① 导航本体的玻璃材质（`depth.css`，深浅两色的遮挡带 + 1px 顶高光 + 内侧泛光）；② 内容卡片相对背景的抬高；③ 导航投在卡片与背景上的光/影。本报告只谈 ② 的一部分和 ③——它们原先都由同一个 SVG 层画。

### 1.2 这一层是怎么来的

```text
时间：2026-10-06，用户授权"在层次感中加入内容卡片相对背景的高度"。
定位：空间关系试验，不是导航性能优化。
禁区：不修改已确认的导航本体受光、宽度、过渡曲线（后来固定为"B 档参数"，
      见 §1.7）；不动 main.css 的材质系统。
当时做法：导航之下挂一层固定 SVG，按"接光面"把屏幕分区，让卡片与背景分别收光。
```

### 1.3 组件机制（`app/components/DepthReceivers.vue` + `app/utils/depth-receivers.ts`）

```text
挂载：首页/错误页的导航之后；SSR 不输出（客户端专属），无观察器则整层不启用
DOM ：<svg class="depth-receivers" width=viewport width height=viewport height
        viewBox="0 0 viewport">           ← 尺寸=视口
      defs 里两张 mask（mask-type: luminance）：
        near 遮罩 = 白=内容卡片矩形(带 rx) + 黑=导航矩形   → 只有卡片被照亮
        far  遮罩 = 白=整屏 + 黑=卡片矩形 + 黑=导航矩形     → 只有"其余区"被照亮
      主体两组 <g>，各含一个矩形，**两个矩形的几何都取自导航自身**
        （x/y/width/height/rx = .site-header 的矩形），
        分别套 far / near 遮罩 —— 所以是"同一光源、按落点分两档强度"
测量：getBoundingClientRect + borderTopLeftRadius；视口取 documentElement.clientWidth
      × innerHeight；长讲义在视口外 96px 处裁切（visibleSurface，防止为几万像素长文
      建立巨大模糊面，且不能裁在可见边缘凭空造出阴影）
监听：onPageScroll → 一次 rAF 合帧测量；ResizeObserver（导航+卡片）；window resize；
      MutationObserver 只看 html 的 data-depth / data-visual / data-display-mode /
      data-color-mode；路由切换后 nextTick 重新绑定
属性：几何有效（有导航 + 至少一张卡片）时设 html[data-depth-receivers='true']；
      否则删除属性 → 旧 CSS 光条回退（depth.css 里靠 --depth-direct-band 变透明）
```

### 1.4 它画成什么样（§2 是精确参数，这里是观感）

```text
近投影：卡片顶部被一层沿顶边的光/暗带压住，最亮在导航正下方，往下 ~30px 内衰减完
远投影：导航下沿之外，整幅背景上一条更宽更弱的同色带，强度只有卡片上的 55%
深浅色：深色模式是"冷白投光"（rgb(220 230 248 / .20 或 .30)）；
        浅色模式反过来是"深灰遮挡影"（rgb(24 30 40 / .11 或 .15)）
滚动态：导航放宽到 calc(100vw - 36px) 后，两层一起淡到 opacity .58
手机  ：近/远的模糊与位移都缩小（见 §2）
禁区内不动：导航本体自己的 box-shadow（内侧泛光 + 1px 顶高光 + 外部遮挡带）
        由 depth.css 的 --depth-glass-* 画，接光层只负责"落到别的面上"的那部分
```

### 1.5 为什么想拆掉它

```text
拖影  ：固定层覆盖滚动容器，必须每帧重测每张卡片 → 测量→rAF→渲染差一帧，影子落在卡片后面
卡顿  ：每帧重渲"每卡一矩形 + 两层大模糊遮罩"；远投影的 blur 作用在视口大小的矩形上
闪回  ：surfaces 为空时整层 v-if 卸载、属性被删、旧 CSS 光条回退，来回闪
GPU   ：成本 ∝ 被模糊像素数 × σ × 帧数；桌面 1180+px、DPR2 时远大于手机视口
```

其中"卡片自己的投影"已被判定为**静态几何**，于 2026-10-06 从 SVG 层搬到 `depth.css` 的静态 `box-shadow`（跟着卡片合成平移、零 JS、不卸载）；留在 SVG 里的只剩导航投影。本报告讨论的就是这一步之后、**导航投影**还能不能也搬走。

### 1.6 过程中已修掉的两个真 bug（只做记录）

## 2. 参照模型（验收基准，全部实数）

### 2.1 参数

| 层 | 落点 | SVG 参数 | 裁剪 |
| --- | --- | --- | --- |
| 近 | 内容卡片 | σ=10px、下移 +8px、填充 α | 只保留卡片范围 |
| 远 | 页面背景 | σ=24px、下移 +28px、填充 α、整体 opacity .55 | 全屏 − 卡片 − 导航 |

```text
手机    ：近 σ8/+6、远 σ18/+22
滚动态  ：两层同乘 opacity .58
过渡    ：只动 opacity，展开 320ms cubic-bezier(.22,.8,.3,1)、收起 520ms cubic-bezier(.4,0,.2,1)
深浅色  ：颜色交换（浅色=深灰遮挡影，深色=冷白投光），不是 alpha 变化
```

### 2.2 换算 ①（最容易错的一条）

```text
SVG filter: blur(x) 的 x 就是高斯 σ
CSS box-shadow 的 blur 半径 ≈ 2σ；位移与 SVG 相同；spread 取 0；颜色 alpha 直接对齐
```

| | SVG | 等价 CSS |
| --- | --- | --- |
| 近 | σ10 / +8 / α | `inset 0 8px 20px 0 color(α)` |
| 远 | σ24 / +28 / α×.55 | `0 28px 48px 0 color(α×.55)` |

（这就是为什么"手调 14/28"看起来像但不对：软硬度差了整整一倍。）

### 2.3 参照模型的本质

```text
两层都锚定在视口：光挂在导航上，卡片从光下穿过。
强度则按"落点属于哪一类"分档。
→ 一个锚点 + 两种衰减。纯 CSS 没有"按落点变强"的能力，这是所有损失的根源。
```

## 3. 方案 A：导航单层 `box-shadow`

```text
实现：让导航自身投一条 box-shadow，取代整层 SVG
  远/近合一：0 28px 48px 0 color(α×.55)   （或折中取值）
  滚动态    ：与导航材质共用 opacity 淡出，沿用 320/520ms
  删掉      ：整个接光层组件、观察器、遮罩、逐帧测量
代价：卡片上的光与背景上的光**同强度** → 参照的"近 : 远 = 1 : 0.55"消失
优点：锚点与参照一致（视口），不会出现"卡片离导航很远时顶边还发光"
```

## 4. 方案 B：背景渐变 + 卡片 `inset`

### 4.1 三层架构（按接收方分层，而不是按发射源）

```text
① 远层：画在"背景接收层"上的一条固定顶部渐变带
   - 几何是常量（导航 top/宽度在断点内固定），零 JS、零滤镜、零遮罩
   - 用 8~10 个色标近似高斯尾部，比 box-shadow 更可控（可单独压尾部避免 8bit 台阶）
② 近层：卡片自己的 inset 顶光，挂在读面（.hero/.latest-section/.manifesto/
        .standard-page/.article-page），静态、随卡片合成平移，只覆盖顶部
③ 导航：只保留材质阴影 + 滚动态淡出（本方案不碰）
```

### 4.2 远层色标算法

```text
α(d) ≈ .55 · α · exp(-d² / (2·24²))        （σ=24，峰值取 .55）
示例（α 为模式底色；深色 rgb(226 234 250)、浅色 rgb(24 30 40)）：
  0px α×.55   8px α×.50   20px α×.40   34px α×.27   52px α×.14   74px α×.06   96px α×0
```

## 5. 损失清单（方案 B；方案 A 的唯一损失已在 §3 写明）

### 5.1 视觉损失（只列"看得见"的，按可见性排序）

| # | 现象 | 何时看得见 | 量级估计 | 缓解 | 残留 |
| --- | --- | --- | --- | --- | --- |
| V1 | **近/远交界的一阶强度台阶**：参照是"同一条光穿过两种接收面"只有渐变；B 是背景层与卡片各画一份，在卡片顶边外侧相接处可能留 1–3px 略亮/略暗细带 | 深色 + 高对比背景（aurora/art）最明显；浅色次之；flat/theme 看不出 | ±2–4/255 | 近层顶部取"近 + 远在该处的贡献" | ±1–2/255 |
| V2 | **横向均匀性方向**：参照近层 = 导航剪影 ∩ 卡片；静止态两者等宽、滚动态导航**更宽**（`width: calc(100vw - 36px)`），两种情况下卡片都被完全覆盖 → 卡片上就是一条均匀带，与 `inset` 一致。**滚动态不是问题**；露馅的是反向情形（卡片宽于导航、居中/窄卡片） | 反向情形才有 | 同宽/更宽时 <1–2/255；反向可达 ±α | 只对与 shell 同宽或更窄的顶级读面生效 | 结构性前提 |
| V3 | **光带尾部是手写曲线**：5–6 个色标近似高斯，尾段形状与连续高斯不同 | 极暗背景上看"光带长度" | 感觉短 3–8px；台阶 1–2/255 | 色标加密到 8–10 个，末段压到 α<1/255 | 需视觉校一次长度 |
| V4 | **"同一光源"一致性丢失**：参照远近同源（同 α 同色，只差 σ/位移/opacity）；B 两处独立定值 | 深浅并排比对、切换轻柔↔鲜明 | 比例偏差 ±3–5/255 | 两档按同一系数生成 | 单独看几乎不可见 |
| V5 | **贴边叠加**：卡片顶边紧贴导航下沿时，inset 与远层在同一处相加；参照因遮罩互斥不叠加 | 只在"正好贴边"的滚动位置 | +3–6/255 | inset 顶部留 1px 缓冲或按 `.58` 同步淡出 | 无法感知贴边，属可接受近似 |
| V6 | **浅色机制观感差异**：参照是"上方有东西挡光"；B 是"卡片自己顶部带灰"，还可能压住材质自带的 1px 顶高光 | 浅色 + 鲜明档 | 观感、难量化 | inset 从顶边下 1px 起、alpha 收一档 | "光的来向"暗示变弱 |
| V7 | **滚动稳定性反而是收益**：参照有拖影/闪回/抖动，B 没有 | 滚动时 | — | — | 收益 |
| V8 | **卡片顶光"永远在"**：参照只在卡片靠近导航（σ10、+8px，约 40px 内）时照亮它；B 的 inset 无论卡片离导航多远都画 | 卡片从下方进入视口、离导航还有上百像素时（如首页第二张卡上升中） | 整条顶光都是"多出来的"，≈ α | **无纯 CSS 解**（要感知距离就得回到逐帧测量） | 结构性，需用户裁决 |
| V9 | **光"粘在卡片上"**：参照的光随导航固定、卡片从光下穿过；B 的顶光随卡片滚动 | 滚动时看卡片顶边 | 观感差异（非亮度） | 无 | 结构性 |
| V10 | **滚动态远层两条小差**：① 参照远光带长度随导航变宽一起拉伸（440ms），B 的渐变带是常量；② 参照把远层从卡片范围完全裁掉，B 的远光会透过半透明卡片隐约透出（卡片玻璃约 30–50% 透光） | ① 展开动画期间；② 卡片顶边落在远层可达范围（约 96px）内 | ① 观感；② 约 2–4/255 | ① 接受，或让远层随 `[data-scrolled]` 动一次 `background-size`；② 远层色标起点下移 | ② 可压到 ≤2/255 |

### 5.2 非视觉损失

```text
L1 维护风险：B 的远层渐变几何是写死的常量。导航 top 在断点间不同（18/10/7px…）、
            导航高度与 shell 宽度变化都不再自动跟随 → 每个断点各写一份，人工同步。
L2 过渡错拍：参照两层共用一套 .58 + 320/520ms；B 若不把远层与近层绑在同一条规则上，
            会出现"卡片先淡、背景后淡"。必须共用一个能被 [data-scrolled='true']
            与 reduced-motion 同时命中的伪元素。
L3 失去响应式跟随：导航伸缩/专注模式改变几何时，参照测量后自动对齐，B 不会。
L4 收益项：关闭态、纸媒、无 JS 下 B 更稳（不依赖观察器与几何判定）；
            反向遮挡（卡片盖住导航上缘）靠 z 序天然成立。
L5 代价转移：删掉逐帧测量、视口级 blur、遮罩、卸载闪烁、--depth-direct-band 开关；
            新增一张固定渐变带（一次栅格化）+ 每张卡片一个 inset（静态）。
L6 未实测：本报告没有任何帧率/GPU 数据，只有结构推断。
```

## 6. 锚点债：为什么 V8/V9 无法用纯 CSS 消除

```text
参照：光锚定视口。卡片从下方升上来时，只有当它进入导航下方约 40px 时才被照亮。
B   ：光锚定卡片（inset 是卡片自己的边），于是"卡片在哪儿，顶光就在哪儿"。
      → 卡片还没靠近导航，顶边就已经亮着（V8）；滚动时光像贴在卡片上走（V9）。
要修 V8 就必须知道"卡片离导航多远"→ 只能测量 → 回到被拆掉的那套东西。
```

**A / B 的真正取舍（决定前只看这一句）**

```text
A（导航单层 box-shadow）＝ 锚点与参照一致（视口），但近/远只能同一个强度
B（背景渐变 + 卡片 inset）＝ 近/远分档保住，但锚点从视口变成卡片，代价是 V8/V9
```

若"卡片上升过程中不该有顶光"重要 → 选 A；若"卡片上的光必须比背景上的光强"更重要 → 选 B 并接受 V8。

## 附录 C 参照模型的数学：从 SVG 滤镜到 CSS 阴影

### C.1 为什么 SVG 能做到"同一光源、两种衰减"

```text
层里只有两个矩形，几何都取自导航自身（x/y/width/height/rx = .site-header 的矩形）。
真正区分近/远的是套在它们外面的 mask：
  near 遮罩：白=卡片矩形（带 rx），黑=导航矩形  → 白区保留、黑区剔除
  far  遮罩：白=整屏，黑=卡片矩形 + 黑=导航矩形 → 与 near 完全互补
遮罩是 luminance（按亮度取 alpha），所以：
  同一块导航矩形，经过 near 遮罩后只剩"落在卡片上的那部分"，
  经过 far 遮罩后只剩"落在背景上的那部分"，中间没有重叠、也没有 1px 缝。
这就是"同一光源、按落点分成两档强度"的全部机制。
```

### C.2 σ 从哪来：SVG 的 blur(x)

```text
SVG feGaussianBlur 的参数是 stdDeviation，即高斯标准差 σ。
CSS filter: blur(<length>) 在 SVG 滤镜等价模型下，同样把这个长度当作 σ。
→ 结论：.depth-receivers__near { filter: blur(10px) } 的 σ 就是 10px，不是 10px 的"半径"。
```

### C.3 box-shadow 的模糊半径是**直径**量级

```text
CSS 规范对 box-shadow 第三个值的定义：阴影用一个"模糊锥"（blur cone）构造，
其高斯近似的标准差 σ = 模糊半径 / 2。
→ 换算 ①：CSS blur 半径 ≈ 2 × SVG σ
```

### C.4 位置怎么对齐（这一步最容易错）

```text
box-shadow 的几何构造顺序：把边框盒按 (dx, dy) 平移 → 按 spread 扩张/收缩 → 再模糊。
模糊不会移动 50% 覆盖率的那条线，它永远落在"平移+扩张后"的形状边缘上。
SVG 那侧同理：矩形先 translateY(8px)，再模糊，50% 线落在平移后的矩形边缘。
→ 结论：offset-y 直接照抄 translateY，spread 取 0，两边的"半亮线"就重合。
```

### C.5 强度怎么对齐

```text
SVG 侧：fill = var(--depth-glass-light)（内含 alpha），远层再乘 opacity .55
CSS 侧：box-shadow 颜色直接写这个 rgba，远层把 alpha 乘 .55（或写 opacity 同理）
注意：SVG 里 fill 与 opacity 是相乘关系，不是相加；CSS 里颜色 alpha 就是最终覆盖率
→ 两边可以一一对应，不需要额外补偿（补偿只发生在 §7 的"近远分档"问题里）
```

### C.6 换算总表（照这个抄）

| 层 | 参照（SVG） | 等价 CSS | 手机 |
| --- | --- | --- | --- |
| 近（落卡片） | translateY 8px、σ10、fill α | `inset 0 8px 20px 0 color(α)` | `inset 0 6px 16px 0` |
| 远（落背景） | translateY 28px、σ24、α、opacity .55 | `0 28px 48px 0 color(α × .55)` | `0 22px 36px 0` |

```text
反例（为什么会"看着像但不对"）：
  若把近层写成 inset 0 8px 28px，则 σ = 14 ≠ 10 → 软硬度比参照宽 40%，
  观感是"模糊带更糊、边缘更看不出起点"，而不是"位置不对"。位置其实是对的。
```

### C.7 参照模型自带的边界条件（写替换方案前必须知道）

```text
1) 近层只覆盖导航下方约 ±3σ ≈ 30px + 位移 8px 的范围。
   → 卡片离导航上百像素时，参照模型**根本不照它**。
2) 导航自身范围从两张遮罩里都剔除，所以玻璃内部不受这两层影响，
   导航的内侧泛光 / 顶高光 / 遮挡带仍由 depth.css 自己画。
3) 长讲义在视口外 96px 处被裁切，避免为数万像素长的文章建立巨大模糊面；
   裁切点绝不允许落在可见边缘（否则凭空出现一道阴影边）。
4) 几何有效（有导航 + 至少一张卡片）才设 data-depth-receivers='true'；
   任何一条不成立就回退旧 CSS 光条，不会出现"半新半旧"。
5) near/far 的互补是"像素级互补"，所以卡片与背景交界处**没有**强度台阶，
   也没有 1px 的缝——这是纯 CSS 方案最难过的一关（§5 V1）。
```

| 7 | 导航伪元素 + `mix-blend-mode`（multiply/screen） | 否（混合作用于整个重叠区，不区分落点） | 是 | 是 | 中 | 只能改变"看起来的颜色"，不能分档；且会污染导航自身材质 |
| 8 | `color-mix()` 生成档位色 | —（是工具不是机制） | — | 是 | 零 | **推荐用于生成轻柔/鲜明两组值**，避免手写 8 个色值 |
| 9 | 把模糊预烘焙成 SVG data-URI 背景图 | 是 | 是（视口） | 是 | 一次解码 | 可替代 scheme 4/1 的 blur，避免滤镜；代价是 8bit 色带与拉伸失真 |
| 10 | **scroll-driven animations**（`animation-timeline: view()` + `animation-range`） | 是 | **可近似**（用滚动进度模拟"接近导航才亮"） | 是 | 需要每卡一条时间线 | **唯一能绕开 V8 的纯 CSS 路线**，见 D.2 |
| 11 | Houdini `paintWorklet` | 能画任意函数（比色标更准的高斯尾部） | 是（屏幕空间） | 是 | 需要注册 worklet；Chromium 外支持差 | 可作为精度升级，不解决分档 |
| 12 | `-moz-element()` / `element()` | 可把导航当图像用 | 是 | 是 | — | 仅 Firefox，不可用 |

### D.2 为什么"分档"必然导致"锚点分裂"

```text
纯 CSS 的绘制单元只有两种自由度：
  (a) 盒子自己的边（inset / 边框 / border-image）
  (b) 一个矩形区域（背景、伪元素、渐变）
而"按落点分档"要求同一个光源在两种区域给不同强度 —— 这需要"按区域裁剪"能力，
CSS 除了 mask-image（需要预先知道区域几何）之外没有别的办法。
于是：
  想把光画在卡片上 → 只能用 (a) 盒子边 → 光随卡片走 → 锚点错位（V8/V9）
  想保住视口锚点 → 只能用 (b) 矩形区域 → 一整片同强度 → 分档丢失（方案 A）
第三条路（D.2.1，未验证）：用 (b) 保锚点 + 用 scroll-driven animation 让卡片顶光
按"离导航的距离"淡入淡出，从而在观感上补回"只有靠近导航的卡片才亮"。
```

#### D.2.1 第三条路的具体设想（未验证，留给将来）

```text
远层：导航单层 box-shadow（方案 A 的远半）——锚点正确、强度 .55α
近层：卡片 inset 顶光，但用滚动进度控制其 opacity：
  - 滚动容器是 .page-scroll（不是文档流），因此 view() 时间线的"视口"就是该容器
  - 每张卡片上挂 animation-timeline: view(); animation-range 让它在"接近顶部"时淡入
  - 观感上接近参照："卡片离导航远 → 顶光淡出；贴近导航 → 顶光满强度"
未验证的点：
  - animation-range 的区间是相对滚动容器视口，不是相对导航高度 → 两者差值需要手校
  - 淡入淡出期间是逐帧合成（只动 opacity，成本可接受，但不再"完全静态"）
  - 与 prefers-reduced-motion 的交互、与 data-scrolled 的 .58 叠加需要另定规则
  - 浏览器支持：Chromium 111+ / Safari 26+ / Firefox 144+（需实测确认本项目目标范围）
结论：这条路是目前唯一可能同时保住"锚点 + 分档"的纯 CSS 路线，
     但复杂度和不确定性都高于 A/B，优先级排在 A/B 之后。
```

### D.3 手段选择建议（按"损失最小"排序）

```text
① 什么都不做（现状）：视觉 100%，性能与闪烁问题原样保留
② 方案 A：锚点正确，丢掉近/远分档（卡片与背景同强度）→ 视觉差异最大的地方是
         "卡片顶部的光不再比两侧背景强"，其余几乎一致
③ 方案 B：分档保住，付出 V1/V2/V5/V8/V9/V10 六条视觉损失，其中 V8/V9 无解
④ 第三条路（D.2.1）：理论最优，但需要动画与浏览器实测，风险最高
⑤ 其余手段（5/6/7/12）：机制上不成立或平台不支持，直接排除
```

## 附录 E 损失数值的推导与假设

> **重要：本节按公式重算后，推翻了 §5.1 表里的三个数字（V1/V8 与"贴边叠加"）。以前者为准。**
> §5.1 是"量级估计"，本节是"推导值"。之所以要重算：写 §5 时用的是"整条光带 ≈ α"的粗算，
> 忽略了**光带是从某条边往外衰减的**，衰减函数决定了误差量级。

### E.1 常量与假设

```text
α（--depth-glass-light 的 alpha）       深色 轻柔 .20 / 鲜明 .30 ；浅色 .11 / .15
σ_near = 10px、σ_far = 24px、位移 8 / 28px、远层 ×.55（附录 B.1）
覆盖率函数 C(d) = Φ((边到点的距离)/σ)，Φ 为标准正态分布函数（模糊边的标准剖面）
d = 该点到"某条边"的距离；D = 卡片顶边到导航下沿的距离（随滚动变化，是本问题的关键变量）
8bit 量化步长 = 1/255 ≈ .0039
假设：卡片玻璃透光率取 30–50%（用于 V10② 的透射估计）；所有数字为上限估计，未经实测
```

### E.2 参照模型在卡片上的真实剖面（这一步决定了一切）

```text
参照：near 矩形 = 导航矩形下移 8px、σ10 模糊 → 在卡片上某点的覆盖率
      C_near(d) = Φ((8 − d) / 10)，d 从**导航下沿**往下量
far ：C_far(d)  = Φ((28 − d) / 24)，d 同样从导航下沿量

d(px)     0     4     8    12    18    28    40    60    80    96
C_near   .79   .66   .50   .34   .16   .023  .001  ~0    ~0    ~0
C_far    .88   —     .80   —     .66   .50   .31   .09   .015  ~.005
```

```text
两个直接可用的结论：
① 参照的近层在卡片上**不是一条恒定强度的带**：它随 d 快速衰减，40px 外基本为 0。
   所以"卡片离导航越远、顶光越弱"是参照的固有行为，不是偶然。
② C_far(96)≈0，正好解释了远层渐变带的色标为什么在 96px 处收尾（附录 B/§4.2）——
   两个独立推导互相印证。
```

### E.3 方案 B 的偏差（按 D 逐档算）

```text
B 的卡片 inset 以**卡片顶边**为锚，offset 8px、σ10 → 在卡片顶边处覆盖率恒为 Φ(8/10)=.79，
与卡片在屏幕上的位置无关。于是"卡片顶边那一点的亮度"对比：

  D(px)     参照近层 C_near(D)   B 的 inset(卡片顶边)   倍数    深色鲜明档换算
  0（贴住）     .79                  .79                 1.0×    一致（唯一对齐点）
  4            .66                  .79                 1.2×   —
  8            .50                  .79                 1.6×   差异 ≈ .087α ≈ 22/255
  12           .34                  .79                 2.3×   差异 ≈ .135α ≈ 34/255
  18（常见）    .16                  .79                 **4.9×** 差异 ≈ .19α  ≈ 48/255
  28           .023                 .79                34×     差异 ≈ .23α  ≈ 58/255
  >40          ≈0                   .79                 无穷    整条顶光都是多出来的
```

```text
换算说明：差异 alpha × 该处底色与本色的对比 → 深色鲜明档 α=.30，
  差异 .19α ≈ .057 alpha ≈ 14/255（同色区内）～ 48/255（高对比底，如 aurora）
取高对比背景作为最坏值，因此上表最后一列是按"卡片顶带与背景对比明显"估的上限。
结论：B 的卡片顶光在**常见距离 D=8–18px 下比参照强 1.6–4.9 倍**，
     D>40px 时参照已无光而 B 仍然满强度 —— 这是一条**会被人眼直接看出来的**偏差，
     不是"±1–2/255 的微差"。
```

### E.4 对 §5.1 的修正（以本节为准）

| 条目 | §5.1 原写法 | 修正后 | 说明 |
| --- | --- | --- | --- |
| V1（交界台阶） | ±2–4/255，补偿后 ±1–2/255 | **不做补偿时上限 ≈ .19α（深色鲜明 ≈ 14–48/255）；"补偿"只能抵消一层常量，无法修正剖面形状** | 参照的 near/far 剖面斜率不同（σ10 陡、σ24 缓），单一静态 inset 无法同时贴合两者 |
| V5（贴边叠加） | +3–6/255 | 只在 D≈0 时成立（此时 B 与参照对齐，误差确实小）；D 增大时误差由 E.3 主导 | — |
| V8（顶光永远在） | "≈ α" | **卡片顶边处 3–5 倍（D=18 时 .79α vs .16α）；D>40px 时为"0 → .79α"，即整条顶光都是多出来的** | 这是方案 B 最重的一条损失 |
| V11（新增） | — | **剖面形状错位**：参照的峰值在导航下沿、向下衰减；B 的峰值在卡片顶边、向下衰减。同一个"带"，亮心位置不同 | 静态几何无法同时对齐亮心与衰减 |

### E.5 什么情况下这些偏差会变小或变大

```text
变小：卡片顶边恰好贴住导航下沿（D≈0）——此时 B 与参照几乎重合；
     浅色档（α 更小）、轻柔档（α=.20）、flat 背景（对比低）
变大：卡片从下方上升的过程中（D 从大变小，B 全程发光而参照几乎无光）；
     深色鲜明档 + aurora/art 高对比背景（对比最大）；
     手机（σ、位移都更小，但 D 的相对比例更大，倍数关系同量级）
```

## 附录 H 易错点与常见疑问（FAQ）

```text
H1 为什么一个 box-shadow 做不出"卡片上更强、背景上更弱"？
   → 一个元素（或一层阴影）只有一个强度，强度不随落点变化；要分档就必须分区绘制。

H2 换算时的三个常见错误？
   → ①把 CSS blur 半径当成 σ（它 ≈ 2σ）；②用 spread 去对位移（位移应由 offset-y 承担，spread 取 0）；
     ③近/远两层照抄同一组 offset/blur（它们本来就不同：8/10 与 28/24）。

H3 卡片影能搬走，导航影为什么不能？
   → 卡片影是"静态几何"：形状与卡片固定，随卡片一起合成平移，零 JS；
     导航影必须跟着视口/导航动态定位，且要按落点分档，所以至今留在 SVG 层。

H4 闪回是怎么来的？
   → 模板用 v-if="enabled && surfaces.length"：任何时刻没有可见卡片，整层卸载、属性被删、
     旧 CSS 光条恢复；下一帧卡片回来又重新挂载 —— 一删一加就是闪。

H5 "光带看着短了 3–8px"该调什么？
   → 调色标（渐变的尾部），不是调模糊。参照的远层 C_far 在 96px 处已≈0（附录 E.2）。

H6 "卡片顶光永远在"能不能用 @media / :has() 修？
   → 不能。CSS 无法得知"卡片顶边离导航下沿多少像素"，那是一个滚动相关的连续量。

H7 那 scroll-driven animation 呢？
   → 可以近似（附录 D.2.1），但需要每卡一条时间线、需要手校区间、需要浏览器支持确认；
     是本报告里唯一可绕开 V8 的纯 CSS 路线，优先级排在 A/B 之后。

H8 为什么不让卡片自己用 backdrop-filter 采样？
   → backdrop-filter 采样的是"卡片背后已经画好的像素"，而导航投影并不在卡片背后
     （导航在卡片上方），机制上不成立。

H9 .58 这个数在干什么？
   → 滚动后导航宽度从 shell 宽拉到 calc(100vw - 36px)，单位面积能量下降，
     所以整层淡到 .58；它是"能量守恒"的近似，而不是随便挑的运维值。

H10 为什么浅色模式是"深灰影"、深色模式是"冷白投光"？
   → 两种模式里导航的身份不同：浅色下它是遮挡物（挡住环境光），深色下它是发光体。

H11 为什么比对只读正中一列？
   → 由用户指定；且正中一列恰好纵切"导航—卡片—背景"三段，是唯一必然出现差异的切面，
     比全图平均更能暴露问题（全图平均会把差异摊平）。

H12 为什么这份报告严禁提交？
   → 它是开发过程记录（与 docs/work-checkpoint.md 同类）；已加入 .gitignore，机制上防止误入版本库。
```
