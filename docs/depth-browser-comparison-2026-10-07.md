本轮用户授权在已启动的 localhost:3000 用 Chrome 与 Edge 诊断；不是重设计或降低材质质量。

## 测试条件与限制

- 初始 Chrome：1707×932 CSS px、DPR 1.5、深色、层次关闭、导航液态玻璃 14px、内容 5px。
- 初始 Edge：767×850 CSS px、DPR 约1.65、深色、层次鲜明、同样的两项模糊。767px 在移动断点内，不运行桌面导航展宽规则。不能直接拿初始两个窗口比较浏览器性能。
- 浏览器视口覆盖受已有缩放影响：同样请求1707×932，Chrome 得1707×932/DPR约1，Edge得1552×847/DPR约1.1。测试必须记录实际值，不能声称请求值就是实际值。
- 浏览器工具禁止访问 chrome://gpu；没有绕过限制，也没有改变浏览器 flags。昨日截图显示的 GraphiteDawnD3D11 / GaneshGL 只作为历史线索，不视为本轮已核实的后端状态。
- 临时 dev-only 插件仅对 `?depthProbe=1` 页面增加按钮，自动测试各组后恢复 depth 属性与滚动位置，不写 localStorage。每组两次往返0/100px，每方向1150ms、组前静置1300ms；记录 rAF 间隔，不是 GPU 呈现帧率。
- 首次 Chrome 所有组均出现约1000ms间隔，连关闭层次也如此。这轮作废：疑似窗口遮挡/后台节流。用户随后确认将 Chrome 放到前台重跑，不能用作废数据评价产品性能。

## 结论与实现边界

1. 用户报告的Chrome明显更卡获得实测支持，不只是初始窗口尺寸不一致。相同CSS尺寸时仍有很大的长尾差异；DPR不完全一致、固定测试顺序和每组有限重复仍是限制，不能将比例推广到所有机器。
2. Chrome两轮保留全部光效、仅停止导航尺寸插值时，均没有超过50ms的间隔；原效果均有9次。结合昨日GPU进程长任务，定位方向是**尺寸逐帧变化与层次特效组合下的绘制/合成路径**，不是主线程业务JS连续运行200ms，也不能只怪内发光一个图层。
3. 内容backdrop去除会改善两款浏览器P95，但Chrome仍有约151–161ms尖峰。说明持续绘制成本与长尖峰不应混为一谈。不是建议删除内容模糊。
4. 不能从rAF直接判定纹理分配、光栅化、滤镜或驱动同步中的具体一项；Graphite/Dawn是历史后端差异线索，不是已证实根因。需要GPU内部细分或缩小复现后才能提出特定后端bug。
5. 下一轮应研究保持现有动画轨迹和光学配方，同时减少被滤镜/遮罩处理的表面逐帧改变尺寸；不要继续仅改亮度时序，也不要给整个导航含文字做scaleX（会拉伸文字与圆角）。此前内发光分片并未单独解决，不能原样重复宣布成功。候选实现须在Chrome相同窗口复录并做视觉对照后才保留。
6. 本轮不修改生产视觉实现。临时dev插件测试结束已删除，各组finally恢复depth和滚动；浏览器临时视口恢复与页面清理随后核验。未提交推送。
