# Inkroam 层次感性能调查全程报告

证据截止：2026-10-13。范围：从最初层次光效与导航展宽卡顿，到本日 Chrome / Edge 重测。本文为已有源码、实测记录和断点的审阅汇总，不是重新运行所有历史实验；没有公开原始 trace，也没有修改产品设计或部署。

## 结论摘要

**问题还没有解决，但问题范围比最初清楚得多。**

- 最初的 Chrome 录制确有很大的绘制/交换前长尾；后续变量局部化在有限对照中减少了长尖峰，但没有改善整体中位间隔。这是部分优化，不是最终修复。
- 目前必须区分两个阶段：导航尺寸变化的共同成本，以及尺寸变化之后开启层次时额外持续的亮度动画成本。静止页面和动画结束后大致恢复到约6.1ms的 rAF 间隔，不能说整页一直卡顿。
- 最新 Chrome155 光效阶段中位25–31.9ms，关闭层次6.2ms；Edge155 恢复DPR1.5后为12.1ms，关闭6.1–6.5ms。支持本机上Edge更流畅的观感，但视口尚有差异、当前自定义背景内容未再次校验，不能宣称严格性能倍率。
- 全部冻结光效会消除对应时间段的额外开销；单独冻结某一层、移除某一项效果往往不够。取消模糊或动画只属于诊断干预，不能以牺牲质感作为交付。
- 尚未证明 Graphite、Dawn、核显或某一个CSS属性是唯一根因。最有价值的下一步是严格受控的渲染链路记录或最小复现，不是再遍历一批 `will-change`。

## 1. 先说明“完整”的边界

本报告覆盖仓库中可找到的全部调查阶段、十轮组合实验、后续分阶段隔离、两批用户trace以及最新复测，并链接原始逐组表格。未保存的逐帧数组、额度中断未返回的结果、没有真实执行的设计提案，均不补造。

早期设计演变由历史文档与对话支撑，有些只有用户反馈，没有可复核的前后计时；这些列为设计/工程记录，不冒充性能实验。10月7日分片版、10月8日后的连续光面版、局部化前后，以及Chrome154/155，不是同一版本，不能拼成一条优化百分比曲线。

### 测量口径

|口径|实际含义|不能据此声称|
|---|---|---|
|rAF间隔|浏览器动画回调之间的时间；本案多数自动对照使用它|实际呈现FPS、GPU执行时间|
|整段rAF分位数|混合了尺寸动画、亮度动画和稳定尾段|纯光效成本、静止成本|
|阶段桶|按间隔起点分0–440、440–1000、1000–1600ms|严格逐帧对齐的真实动画边界|
|提交至呈现等异步trace跨度|包含排队、同步、执行与等待的墙钟延迟|将倒数当FPS，或相加当总GPU时间|
|GPU进程RunTask / GPUTask|CPU线程侧记录，可能含驱动等待|shader真实耗时、显卡算力不足的证明|
|computedStyle|干预和最终样式是否实际命中|逐像素一致、视觉验收已完成|
|源码门禁/类型检查|代码契约和静态正确性|浏览器流畅、GPU性能达标|

## 2. 最初阶段：设计扩展与性能问题混在了一起

### 2.1 光效的设计取舍

早期尝试从边沿光、整片光带、上下偏重渐变，发展到用户认可的玻璃内部均匀受光、字形/图标投光与彩色标识透光。部分版本被评价为塑料感或不符合光源直觉，已撤回。它们是审美迭代，不是性能胜出方案。

10月5日记录曾用中间70%行平均判断横带；后来改为中心单列像素检查，发现多个弱层叠加与量化台阶，旧口径被作废。该像素检查属于视觉证据，不可用来证明GPU瓶颈。

导航滚动展宽后，光效应减弱。最初对大模糊阴影和背景逐帧插值的版本被用户反馈卡顿，随后改为装饰层opacity渐变。**“opacity通常更适合合成”没有保证本页面组合效果便宜，后续实测恰好说明不能仅靠这一规则下结论。**

用户最终选择B档滚动外部环境光：深色.20→.17、.30→.26，浅色.11→.095、.15→.13。此后这些终值是保留设计，不应因优化随意减弱。

来源：[层次设计及视觉历史](depth-design.md)。

### 2.2 内容高度引入与真实bug修复

10月6日近/远接光模型用于区分导航落在内容卡片与背景上的光影。该功能是空间关系扩展，**不是已经测得有效的导航性能优化**。

|事项|实际处置|证据边界|
|---|---|---|
|全页模糊|Vue scoped/global选择器编译误落到根元素，修正完整后代选择器并检查编译产物|真实视觉bug修复，不是性能收益|
|接光组件未解析|自动导入清单问题导致组件未挂载，改显式导入|解决组件缺失，不等于卡顿修好|
|卡片自身阴影跟随问题|从固定SVG搬到卡片静态box-shadow|简化静态几何的更新路径；没有同口径帧耗时收益保证|
|SVG挂载/旧光条闪回|启用期保持挂载，接管条件不依赖至少一张可见卡片|生命周期修复|
|绘制范围与测量|顶部绘制范围保留6σ余量、缓存卡片坐标、合帧、同值不写和稳定数组引用|合理工程优化；6σ不等于数学零尾部，未证实彻底消除GPU成本|
|透明填充替代inset、删除阴影项|用户要求恢复质感后撤回|不得当成当前实现或优化成果|

纯CSS方案A（单一导航阴影）和B（背景渐变+卡片inset）仅作论证，因锚点、近远衰减和空间关系损失暂缓。历史文档中的“无解”仅适用于所比较方案；估算像素差、滤镜面积与成本公式不是实测。

来源：[接光实现与撤回记录](depth-receivers.md)、[CSS历史提案](depth-projection-css-approximation.md)。本机更早讨论保存在 `docs/depth-projection-open-issue.md`，可能不纳入Git。

### 2.3 延迟光效与分片尝试

按用户建议，将桌面光效变化延后440ms，避免与几何变化同时发生。随后尝试固定宽度分片内光；未证明性能问题解决，且Logo右侧产生竖线接缝，最终恢复单一连续光面。

用户又将变淡时长从320ms延长到480ms，恢复亮度仍520ms。**440ms等待、480ms变淡、520ms恢复只是目前临时观感方案，不是解决性能后的最终动效设计。** 当前优化不能把它永久化为已完成方案。

## 7. 10月10日：透明层、长帧API、第二批trace与材质隔离

### 7.1 单独停用透明回退层没有收益

确认 `site-header::after` 投影本来透明后，临时content:none。基线光效段约23.6–26.8ms，候选24.2–27.2ms，没有可信改善。此项与“全部动画一起冻结”不同，不应混为矛盾结论。

### 7.2 Long Tasks / LoAF不是慢帧内部原因的答案

首次采集出现≥500ms而中止，runs为空；唯一1000ms LoAF不能归因GPU，也不能无证据责怪用户离开。用户指出新标签没有显示，复用原标签重试成功。

有效轮仍为鲜明光效24.1–27.1ms、关闭6.1ms。Long Tasks为0；15条LoAF中11条起点落在采样窗口内，全在几何段，blockingDuration为0、scripts为空，render尾部约.5–1.3ms。

LoAF记录>50ms，而本案亮度阶段主要24–27ms，因此“没有亮度LoAF”不等于该段没有问题，也不能把未解释的时间全算给GPU。

## 12. 流程反思：为什么用了很多额度，仍没有最终解

1. 早期设计扩展与性能定位混行，增加了变量和回归问题。应先冻结视觉基准，再改内部实现。
2. 多轮CSS排除法信息量有限，太晚转入分阶段/trace。后来已经证明单项隐藏和图层提升常常不够，继续重复无意义。
3. 初始视口、DPR、前台可见性没有完全控制；新标签未显示、按钮未真正启动也浪费时间。可见页面不等于持续有效采样，应确认disabled、完成结果和错误状态。
4. 多次没有及时落盘，额度或上下文中断扩大恢复成本。现在必须每轮保存环境、完整摘要、有效性和下一步，不只口头结论。
5. 最大值下降曾容易被误解为全部修好；平均/整段中位也容易掩盖阶段差异。应该用阶段结果、前后基线和trace互相约束。
6. 有些历史文字把猜测写得过硬，如“全屏重绘”“零成本”“CSS无解”。本报告将它们降回受限判断，不把修辞当测量。

## 13. 剩余问题与下一步停止条件

**已知：** 动态光效与现有材质组合存在持续额外成本，Chrome在本机更明显；静止正常；不是一项长业务JS任务的充分解释。

**未知：** 具体哪些离屏表面被重新绘制/采样，Chrome与Edge差异来自何处，怎样在保留轨迹与光学关系时降低成本。

下一阶段应只做一个能提供新信息的实验：锁定同视口/DPR/背景/版本与前台条件，记录当前实现的渲染/栅格/合成轨道；或把导航光面+接光+内容backdrop缩成可复现小页面，逐步恢复依赖。浏览器工具不提供trace时由用户录制，不绕过工具限制。

在取得新证据前，不重复：单纯will-change/translateZ/isolation、外层SVG opacity、只停透明回退层、简单内部span材质迁移。取消模糊/尺寸动画/投光仅作诊断，绝不能当最终修复。

最终验收需同时满足：基线/候选交错复测有稳定阶段收益；终值、动画轨迹、文字圆角和近远关系不退化；深浅主题/轻柔鲜明/移动端/减少动态效果/快速反向滚动/路由切换验证；源码、类型、构建检查完成。未达到这些条件，不宣布完成，也不给虚假的完成百分比。
