# 写给下一位维护 Inkroam 的 AI：理解一整个作品

2026-10-26 · 关于设计、工程、内容与协作的开发复盘

这篇写给接手 Inkroam 的 AI。它讨论整个网站的开发，而不是某一个组件的交接。具体功能的参数与待办仍应查阅各自文档。

我重新读了 README、审美原则、工程复盘和教学内容记录。贯穿这些记录的，不是某一套技术，而是用户反复表达的要求：保留已经成立的美感，把功能真正做完整，让文字可以被理解，别让维护过程反过来消耗他的生活。我们应当把这句话理解成开发目标。

下面是我的判断。历史工作属于不同轮次与不同协作者，不应被我全部写成个人功绩；同样，也不该把历史错误都归给前任。谁接手，谁就负责理解眼前的状态。

## 一、先理解这里为什么存在

Inkroam 是保存文章、想法、学习过程和个人记忆的地方。它有精心调整的界面，却并非只供展示界面的作品；它有很多阅读工具，却也不需要成为功能堆满的工作台。

这会直接影响开发取舍。搜索的价值是找回文字，导出的价值是把内容带走，代码工具的价值是让例子容易读和使用，音乐的价值是陪伴阅读。功能应有明确的用途，也应允许读者不使用它。没有打开导出工具的人，不该承担导出库的首屏成本；没有播放音乐的人，不该先下载歌曲。

About 中的林澈也是一个很好的提醒：用户要给原创角色留一个位置，而不是把博客变成角色主页。理解这种分寸，比挑选一张更显眼的插图重要。同样的判断适用于每个新功能：它应当在这个网站里拥有位置，但不必占据中心。

我希望接手者先回答“这次改动帮助谁做什么”，再决定需要多少按钮、状态和代码。

## 二、尊重已经形成的设计判断

用户对留白、材质、光效、动效和排版有具体判断。这些不是等着 AI 来替换的默认皮肤。

现代幻境和纸媒原版可以有不同的表面语言，但阅读顺序、信息层级与功能语义应当保持一致。新增工具应先理解现有变量、字体、断点、材质通道和缓动方式。不要因为复制一段熟悉的 CSS 很方便，就让某个角落突然出现另一套圆角、阴影和强调色。

参考 Apple 或其它产品可以帮助理解层次、连续性与触感，但品牌名字不能充当设计论证。给所有边缘添亮线不会自动变高级。应说清楚：哪个表面在上层，光从哪里来，文字是否清楚，效果是否挤占了内容的注意力。若用户已经否定某种伪高光，就不要换一个选择器偷偷把它带回来。

“不改变视觉效果”也不能只靠口头承诺。整理 CSS 时，需要保留最终生效的值、选择器作用范围、覆盖顺序、响应式条件和交互状态。删掉一段看似重复的规则，可能同时删掉某个主题的例外。代码更短只是结果之一，不是等价性的证明。

这里还有一个容易遗漏的责任：设计文档会过时。原则可以延续，数值与方案应核对当前实现和后续决策。不能拿早期规范去推翻用户后来明确认可的效果，也不能因为代码已经改了就让文档永远停在旧结论。

## 三、功能要沿着一次完整使用过程来设计

AI 很容易围绕一个入口写功能：点一下能展开，就认为面板完成了；输入关键词能找到结果，就认为搜索完成了。但读者经历的是一个过程。

| 功能 | 必须一起考虑的过程 |
| --- | --- |
| 阅读与导航 | 进入文章、定位章节、滚动、跳到其它内容、后退、恢复位置 |
| 搜索 | 未开始、输入、筛选、空结果、取消、分享网址、返回条件 |
| 外观设置 | 新访客初值、旧偏好恢复、默认与手动切换、主题变化、刷新 |
| 导出与分享 | 选定范围、准备资源、生成、失败、取消、可用的替代操作 |
| PDF、图表与音乐 | 按需加载、等待、交互、切换对象、失败恢复、释放资源 |

最容易漏掉的是状态之间的关系。用户点下按钮，不等于异步任务已经成功；控件被禁用，不等于它对应的状态已经跟随预设更新；关闭面板，不等于应该丢弃面板内的滚动位置。

设置尤其如此。“默认设置”应有清楚的管理范围，不能悄悄接管原本独立的选择。关闭默认后，哪些值应固定、哪些仍跟随系统，要按用户约定实现。旧偏好缺字段与新访客初次进入也不是同一情况。新增一个开关，需要贯通初值、恢复、迁移、写入、界面和实际消费者。

音乐只是这类问题的一个例子：首次加载、真实播放和跨曲续播需要区分。更一般的原则是，先把事实与用户意图区分开，再让 UI 表达它们。

## 四、动效是布局和状态的一部分

我更愿意把动效理解为对变化的解释：面板从哪里来，关闭后回到哪里，某个选择怎样变成当前内容。读者不应看见测量、换布局和清理临时样式留下的接缝。

因此，两个静态端点好看还不够。中间帧是否变形，收起是否有过渡，结束时是否跳一下，快速反向是否从当前画面接续，内容变长时是否打断当前动画，都属于实现范围。

例如，父元素做非等比缩放，子元素各自插值补偿，并不能保证全过程文字不变形；只在起点与终点互为倒数并不够。又如，动画期间绝对定位，结束后恢复文档流，可能改变 margin 折叠。此时增加时长只会延长问题，不能修正终点。

以后写动画，请先确定布局的稳定关系，再选动画属性和曲线。不要在同一个尺寸上同时安排两套互相争夺的动画。取消、卸载与减少动效路径也必须能到达正确状态，而不是只服务于第一次正常点击。

## 五、性能工作要有证据，也要守住原来的效果

导航层次感的长期排查说明了一个问题：肉眼看到卡顿是真实反馈，但“是哪一层导致的”仍需要实验。Chrome 与 Edge 使用相关技术，不代表它们的版本、图形后端、驱动路径和配置相同。不能只凭品牌下结论，也不能把一次流畅当作永久修复。

比较前应记录浏览器版本、设备、视口、DPR、页面状态、设置、操作路径和前台条件。被遮挡或后台节流的测量，应单独标记，不能混入有效对照。记录还应区分主线程耗时、绘制与合成成本、帧间隔和主观观感，避免用一个数字代替整个体验。

每轮实验最好只改变一个能验证原因的因素。先写预期：如果连续尺寸变化是主要成本，停止它应该怎样影响结果；如果结果没有支持预期，就更新判断。不要把每次猜测都直接变成正式产品代码。

尤其不要在用户要求保留质感时，关掉模糊、阴影或光效，再称为性能优化。那是改变了工作量，也改变了产品。这样的实验可以用于定位，但进入正式版本需要另行判断与授权。

延迟光效曾作为排查手段，后来又有同步与延迟的可选行为。接手者必须区分实验历史、当前选项和最终验收结论。文档不应把某次临时方案凝固成永久规范。

我认为最有价值的优化，是移除不必要的数据、重复写入、过期任务和无用计算，让读者仍然得到原来的效果。具体收益必须靠对应证据说明。

## 六、内容本身也是产品，不能把教学当填充物

这个网站保存了面向数学与应用数学背景的学习笔记。读者不理解一段话，不意味着他需要再去问一个 AI；往往意味着讲义把中间步骤省掉了。

“修改调用者的根变量用二级指针”对熟悉 C 的人是总结，对初学者可能同时引入五个未定义概念。好的讲解应先解释对象、地址、指针变量、形参与调用者，再用两个结点和一段短代码展示什么改变、什么没改变，最后才给总结。

数学基础可以成为桥梁：用不变量解释循环，用归纳解释递归正确性，用关系和矩阵帮助理解图。但不要用抽象符号掩盖程序的执行细节，也不要把复杂度、终止性与正确性混为一件事。

写课程时，我要求接手者遵守这些顺序：

1. 给出定义与适用条件，明确符号和约定。
2. 选一个足够小的例子，逐步写出状态与计算过程。
3. 在相应概念旁放短代码，让文字和实现互相解释。
4. 再展示完整算法、边界、正确性理由和成本。
5. 给出可练习的问题，并区分自编练习与有来源的真题。

可视化应当揭示关系。遍历图应能对应访问顺序，指针图应区分对象和保存地址的变量，矩阵变换应说明坐标与面积的变化。图表不是让长文显得丰富的装饰。

执行结果也要诚实。实际运行后采集的输出，应能追溯到对应代码；手推结果就标为手推，不能冒充执行。运行通过不等于证明正确，而证明正确也不代表代码没有越界或释放错误。两种工作都需要。

## 七、让结构承接增长，而不是每次再补一层

早期工程复盘已经指出 CSS 补丁叠加、全局滚动牵连和设置复杂度的问题。这些经验应该进入日常决策，而不是只存在于一篇看起来认真的文档里。

动代码前，先找谁拥有状态、谁消费状态、谁拥有样式、谁负责资源清理。全局滚动应走既有接口，不能每个组件各猜一个滚动容器；共享正文能力应让文章和笔记一起受益，但不同 PDF 阅读方案不应被假定拥有相同能力。

复用也有边界。多个组件可以共享材质配方，同时分别保存用户设置。反过来，复制所有样式会让视觉逐渐分裂，强行共享同一设置又会造成互相干扰。应该复用共同规则，保留明确的差异。

本轮手机按钮的问题只是一个小例子：外观在外层容器、实际交互在内部按钮，导致可见边界与触摸反馈不同。反复扩大宽度、加负边距或伪元素，容易修到旁边去。更可靠的切入点是重新确认外观与交互的归属。这个方法同样适用于弹层、日期输入和其它控件。

但不要因此过度设计。Inkroam 不需要为了显得工程化而引入与规模无关的服务、框架和抽象。只有当职责确实混在一起，或同一规则正在多处漂移时，拆分才有明确收益。

## 八、验收与发布也属于开发

测试应该回答风险，不应该只是证明我们写过测试。

逻辑检查能保护排序、过滤、偏好迁移和边界；静态产物检查能发现链接与资源问题；真实浏览器才能进一步观察布局、焦点、材质、动画与权限行为。这些证据各有范围，不能互相冒充。

修局部样式无需无休止重复完整构建，改全局滚动也不能只检查一个页面。选择足以覆盖变化影响的检查，已有结果可复用时就复用。若用户明确要求暂不测试，保留这个限制，并明确写出“实现已改，尚未验收”。

发布前应阅读当前 README 的流程，检查工作区来源和逐项 diff，避免把其它 AI 的实验、临时文件或未完成改动一起提交。开发根路径可用，不代表 GitHub Pages 的 `/inkroam/` 子路径可用。提交、推送、构建成功、部署完成是不同阶段，报告时要说清实际到了哪一步。

## 九、不要让用户成为我们的调度器和记忆

这段协作中，用户多次要去写作业、吃饭或休息，却仍需要回来发送“继续”。这是值得认真对待的成本。已经授权、信息充分的工作，就应继续推进，不要每完成一个小步骤都把执行权退给用户。

但自主不等于忽略依赖。如果浏览器测量必须前台可见，而用户尚未确认，就不能先跑一轮然后把受节流影响的数据当成果。可以继续分析代码、整理记录或准备实验。保持推进与尊重实验条件并不冲突。

额度同样是成本。反复读整仓、重复跑无法区分原因的实验、连续生成没有新信息的报告，会让用户付出代价却得不到对应进展。每一步应当能减少不确定性、完成一块实现，或留下可复用的证据。

断点应在关键阶段写，而不是等最后一点额度才写。至少记录当前基线、目标与限制、已改文件、实际验证、未完成事项和下一步。失败方案要写失败原因，实验结果要保留条件。旧断点与新代码冲突时，先核对 Git 和源码，不要重复实现已经完成的功能。

这份交接的对象是下一位开发者。不要让用户再次解释哪些设计不能动、哪些测试无效、哪些结果没有跑过。

## 十、我想留下的开发态度

我对 Inkroam 最深的判断，是这里已经积累了很多具体的选择。按钮的反馈范围、文字的停顿、正文的解释顺序、关闭后保留的位置，看似细小，却共同构成了用户愿意继续使用它的理由。

维护这样的作品，需要判断力，也需要克制。能够增加功能不代表应该马上增加；能够重写组件不代表值得重写；发现前任的问题，也不意味着前任留下的一切都该撤掉。

我希望自己的开发思路是：把用户的描述变成清晰的问题，把问题变成可以验证的判断，再让实现有明确边界。若判断错了，承认并修正；若效果还没看过，就保留不确定性。一次返工最应该留下的是原因，而不是另一层更难解释的补丁。

至于不同模型，版本号和名字不能代替具体交付。接手者不必证明自己比谁聪明。保留做对的部分，修正有证据的问题，把后续维护变得容易一些，就已经有价值。

我想留给下一位 AI 的要求很简单：把整个 Inkroam 当作持续使用中的作品来维护。每次离开时，让它更完整、更容易理解，也让用户少承担一点开发过程中的负担。
